# Development Seed Data

## Purpose

`dev-seed/` creates repeatable, synthetic development data for the complete
local platform flow:

```text
Auth → Customer → Catalog → Inventory → Cart → Order → Payment
     → Fulfillment → Shipment → Tracking
```

The running services are the only source of truth. The seed tool uses their
HTTP APIs and never connects to another service's database or imports its JPA
entities.

## Source / Reference

The frozen coffee metadata was informed by the publicly visible [Blue Tokai
roasted-and-ground collection](https://bluetokaicoffee.com/collections/roasted-and-ground-coffee-beans).
It is a reference source only. The local products use the original
`Hearthline Demo Roasters` identity, original concise descriptions, generated
SKUs, and generated identifiers returned by the services.

`scripts/extract_catalog.py` can retrieve the collection into
`data/source-extracted.json` for review. The application never scrapes this
site at startup and never depends on it being available.

## Data Provenance

Every product in `data/products.json` records `sourceName`, `sourceUrl`,
`sourceReferenceTitle`, `sourceExtractedAt`, and an explicit reference-only
usage note. Prices and tasting characteristics are demo/reference values, not
commercial prices for this business.

## Important Image Licensing Notes

The 25 checked-in PNGs under `images/` are simple original geometric bag
illustrations generated by `scripts/generate_demo_images.py`. They do not use
Blue Tokai logos, layout, branding, or downloaded product photography. The
catalog image API owns the uploaded image records; source image URLs are never
used as primary image identity. If a future refresh collects public image URLs,
keep them as provenance metadata and review licensing before distribution.

## Dataset Contents

| Resource | Frozen dataset |
| --- | ---: |
| Categories | 8 |
| Products | 25 |
| Variants / SKUs | 75 |
| Local product images | 25 (one primary image per product) |
| Inventory locations | 3 |

| Development customers | 8 |

`data/products.json` contains the normalized product, variant, attribute,
pricing, provenance, and image metadata. `data/inventory.json` contains the
location, receipt, reservation, and adjustment plan. `data/customers.json` and
`data/scenarios.json` contain only synthetic `example.test` identities and
stable scenario references.

## Categories

The category hierarchy is `Coffee` with `Single Estate`, `Blends`, `Sampler
Packs`, and roast-level children. The API returns the real category UUIDs in
`manifests/seed-manifest.json` after a run.

## Products

There are 25 original demo product names. Each product is `ACTIVE`, has an
original description, and carries roast level, drinking preference, flavour
profile, equipment, and tasting-note attributes where supported by the
Catalog variant attribute map.

## Variants

Each product has Whole Bean / 250g, Ground / 250g, and Whole Bean / 500g
variants. Combinations are deterministic and are represented as Catalog
variant attributes rather than a new service-specific schema.

## SKUs

SKUs are uppercase, readable, stable, and generated from the local product
names, for example `HIGHLAND-COCOA-WB-250`. Catalog returns the authoritative
variant UUIDs; the seed tool never uses a source handle or Shopify ID as an
identifier.

## Product Images

Images are uploaded through `POST /api/v1/products/{productId}/images` as PNG
multipart requests. The catalog response stores the service-owned image URL,
original filename, content type, size, and sort order. A missing source site
cannot break local storefront images.

## Inventory Locations

The tool creates or reuses `WH-MUM`, `WH-DEL`, and `WH-BLR`. Location codes and
receipt references are the stable business keys.

## Inventory Units

Every one of the 75 SKUs receives 2 units in Mumbai, 1 in Delhi, and 1 in
Bengaluru: 300 itemized physical units total. The Inventory API generates
physical UUIDs and unit codes; the stable receive `referenceId` makes a rerun
return the same units rather than creating more. The run also creates a
deliberate 2-unit reservation, one `DAMAGED` unit, one `LOST` unit, order
reservations, and `SOLD` units for the delivered scenario.

## Customers

Eight fake customers use `demo.customer01@example.test` through
`demo.customer08@example.test`. The Auth password is supplied through
`SEED_DEMO_PASSWORD` and defaults only to the clearly development-only
`DemoSeedOnly!2026`; it is never written to the manifest.

## Addresses

Each customer gets one synthetic default `SHIPPING` and one default `BILLING`
address with country `IN`. Address snapshots are copied by the Order API at
checkout; the seed tool does not write Order address rows directly.

## Carts

Customer 03 retains an active multi-item cart and Customer 02 retains an empty
cart. Customer 01's cart is converted by the real checkout endpoint. Adding to
a cart does not call Inventory reservation APIs.

## Orders

Stable idempotency keys create five orders:

- `DEMO-ORDER-001`: two Highland variants with captured, delivered, and refunded sandbox flow.
- `DEMO-ORDER-002`: sandbox payment failure and failed order scenario.
- `DEMO-ORDER-003`: captured order with in-transit shipment.
- `DEMO-ORDER-004`: captured order with out-for-delivery shipment.
- `DEMO-ORDER-005`: pending payment with no shipment.

Order prices are snapshots from the Catalog response. For the historical-price
scenario, the seed temporarily stages `Highland Cocoa` at INR 700 while
creating `DEMO-ORDER-001`, then restores its current demo price of INR 799.
Reruns reuse the same order and stable variant IDs.

## Payments

Payments use the repository's `SANDBOX` gateway only. The tool sends signed
local sandbox webhooks to produce `CAPTURED`, `FAILED`, `PENDING`, and
`REFUNDED` examples. It never fabricates a production gateway success.

The authenticated Order internal callback at
`POST /internal/orders/{orderId}/payment-events` applies a captured payment
through `PAID` to `CONFIRMED`, making the normal Shipping contract usable.

## Fulfillments

Captured orders are passed to the Shipping Service internal fulfillment API.
Fulfillments copy the immutable Order shipping snapshot and reference the
Order's itemized reservation/unit IDs.

## Shipments

Captured scenarios use the deterministic `SANDBOX` carrier. Shipment creation
is idempotent and uses the exact InventoryUnit references returned by Order.

## Tracking

Signed sandbox carrier webhooks create `IN_TRANSIT`, `OUT_FOR_DELIVERY`, and
`DELIVERED` tracking events. The delivered order confirms its reservation via
the Inventory API, so sold units are created through a supported workflow.

## Demo Scenarios

The frozen scenario file covers catalog browsing, an active cart, checkout,
payment failure, payment success, partial inventory, in-transit shipping,
out-for-delivery shipping, delivery, cancellation-compatible order states,
and the historical-price snapshot case.

## Seed Commands

Run from the repository root. Set `SEED_ENV` explicitly; there is no automatic
seed on application startup.

```bash
cd /Users/mihirchittora/Desktop/my-ecommerce
export SEED_ENV=development
export SEED_ADMIN_EMAIL=admin@example.com
export SEED_ADMIN_PASSWORD='Admin123!'
export AUTH_SERVICE_URL=http://localhost:8085
export CATALOG_SERVICE_URL=http://localhost:8081
export INVENTORY_SERVICE_URL=http://localhost:8082
export ORDER_SERVICE_URL=http://localhost:8083
export CART_SERVICE_URL=http://localhost:8084
export CUSTOMER_SERVICE_URL=http://localhost:8086
export PAYMENT_SERVICE_URL=http://localhost:8087
export SHIPPING_SERVICE_URL=http://localhost:8088
export PAYMENT_TO_ORDER_SERVICE_TOKEN=dev-payment-to-order
export ORDER_TO_SHIPPING_SERVICE_TOKEN=dev-order-to-shipping
export PAYMENT_SANDBOX_WEBHOOK_SECRET=dev-sandbox-webhook-secret
export SHIPPING_WEBHOOK_SECRET=dev-shipping-webhook-secret

./dev-seed/seed.sh
```

Progress is printed as `[1/10]` through `[10/10]`. Tokens and passwords are
never printed or persisted. The first run requires all backend services and
their dependencies to be healthy.

Offline commands:

```bash
./dev-seed/seed.sh --validate-only
./dev-seed/seed.sh --refresh-source
./dev-seed/seed.sh --refresh-images
```

`--refresh-source` writes a review artifact only. It does not import changes
into the application dataset. `--refresh-images` regenerates only our local
PNG assets.

## Reset Commands

Reset is intentionally a full local development database reset because the
current services do not expose safe selective deletion for orders, payments,
shipments, and physical inventory units. It targets only the eight named
Compose files in this repository and requires both an explicit `--reset` and
`SEED_ENV=development`:

```bash
SEED_ENV=development ./dev-seed/seed.sh --reset
```

This stops those local Compose projects and removes their named development
volumes. Never run it with production Compose files or production credentials.

## Environment Variables

Required service URLs are listed in the command above. The following are also
supported:

| Variable | Purpose |
| --- | --- |
| `SEED_ENV` | Must be exactly `development` or `test` for data mutation |
| `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` | Local admin JWT for Catalog/Inventory/image APIs |
| `SEED_DEMO_PASSWORD` | Development customer password, minimum 12 characters |
| `PAYMENT_TO_ORDER_SERVICE_TOKEN` | Order internal payment callback token |
| `ORDER_TO_SHIPPING_SERVICE_TOKEN` | Shipping internal fulfillment/shipment token |
| `PAYMENT_SANDBOX_WEBHOOK_SECRET` | Local payment webhook HMAC secret |
| `SHIPPING_WEBHOOK_SECRET` | Local carrier webhook HMAC secret |
| `DOCKER_COMPOSE_BIN` | Optional Compose command, default `docker compose`, used only by reset |

## Idempotency

Categories and products are found by slug. Catalog variants use stable SKUs.
Inventory receives use stable per-SKU/per-location references. Reservations,
orders, payments, refunds, shipments, and webhooks use stable reference or
`Idempotency-Key` values. Rerunning the command therefore reuses existing
records and does not add duplicate products, SKUs, units, orders, payments, or
shipments. A mismatched existing SKU set fails closed and asks for the explicit
development reset.

## Troubleshooting

- `401` or `403` during Catalog/Inventory: confirm the admin account has the
  repository's Catalog and Inventory permissions and that its password matches
  `SEED_ADMIN_PASSWORD`.
- `service is unavailable`: start Auth, Catalog, Inventory, Order, Cart,
  Customer, Payment, and Shipping and check each `/actuator/health` endpoint.
- Payment capture does not confirm an order: ensure Order has
  `PAYMENT_TO_ORDER_SERVICE_TOKEN` matching the seed environment and that
  Payment can reach `ORDER_SERVICE_URL`.
- Shipping cannot create a fulfillment: wait for the Order outbox worker or
  rerun; fulfillment creation is idempotent by Order.
- A changed dataset requires a review and a new `seedVersion`; do not refresh
  source data automatically during application startup.

## Production Safety

The seed refuses to mutate data unless `SEED_ENV=development` or `SEED_ENV=test`
is explicitly set. Production and staging startup scripts do not invoke it.
Reset additionally requires `SEED_ENV=development` and an explicit `--reset`.
No real customer information, production credentials, source logos, or source
images are included.
