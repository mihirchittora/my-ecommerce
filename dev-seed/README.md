# Demo Seed System

## Purpose

`dev-seed/` creates deterministic, synthetic development data for the local
platform flow:

```text
Auth → Customer → Catalog → Inventory → Cart → Order → Payment
     → Fulfillment → Shipment → Tracking
```

The runner uses the running services' HTTP APIs. It does not connect to or
write another service's database.

## Data Source / Reference

The dataset uses [Meesho](https://www.meesho.com/) only as a public reference
for marketplace breadth and visible category/product variety. It is not a
clone and does not copy Meesho branding, UI, identifiers, seller data, customer
data, marketing copy, or hosted images. `scripts/extract_catalog.py` can save a
review-only HTML reference artifact; that artifact is never imported at runtime.

## Categories

The frozen dataset has 10 top-level categories and 38 subcategories:

Women's Fashion, Men's Fashion, Kids, Footwear, Bags & Accessories, Beauty &
Personal Care, Home & Kitchen, Electronics, Home Decor, and Tools & Lifestyle.
Every top-level category has 2-4 populated subcategories.

## Products

There are 37 original product names. Each product is `ACTIVE`, has useful
customer-facing copy, a current Catalog slug, a brand where appropriate, and
at least one active sellable variant. Catalog only receives fields supported by
its DTO: name, description, brand, category, variant attributes, price, and
currency. Material, color, size, storage, pack size, and similar discovery data
are represented in Catalog's variant attribute map.

## Variants

The dataset contains 111 variants across fashion, kids, footwear, accessories,
beauty, home, electronics, decor, and tools. It deliberately mixes color/size,
storage/color, pack-size, volume, and resistance/fit models.

## SKUs

Every variant has a unique deterministic uppercase SKU, for example
`MFT-TSH-COTTON-BLK-M` or `ELE-PHN-NOVA-BLU-128`. SKUs are business identifiers;
the services still generate their own UUIDs.

## Images

There are 91 local PNG assets. Products intentionally have 1, 2, 3, or 4
images to exercise primary-image rendering, galleries, thumbnails, and mobile
swiping. The artwork is deterministic local geometric demo art generated by
`scripts/generate_demo_images.py`; the storefront and services do not depend on
Meesho-hosted URLs.

Each image record includes filename, alt text, primary flag, sort order,
`sourceName`, `sourceAccessedAt`, and internal provenance. Image uploads use
Catalog's multipart endpoint:

```text
POST /api/v1/products/{productId}/images?sortOrder={n}
```

Provenance is kept in the seed files and is not sent in Catalog product copy or
exposed as customer-facing metadata.

## Inventory

The runner creates or reuses `WH-MUM`, `WH-DEL`, and `WH-BLR`. It receives 242
physical InventoryUnits through Inventory's receive API using stable receipt
references and barcodes. It then exercises the supported adjustment,
reservation, release, and confirmation operations.

The frozen plan includes available, low-stock, out-of-stock, reserved, sold,
damaged, and lost examples. Cart writes do not call reservation APIs. Sold
units are produced by confirming real Order reservations after delivery.

## Customers

There are 10 synthetic Auth users and Customer profiles using
`demo.customer01@example.test` through `demo.customer10@example.test`. Each
profile receives one default synthetic SHIPPING address and one default
BILLING address. No production credentials or real customer information are
used. The development password comes from `SEED_DEMO_PASSWORD` and is never
written to the manifest.

## Carts

Seven cart scenarios seed active carts, and the first cart is converted through
the real Cart checkout endpoint for the end-to-end order flow. The Cart API
stores SKU/quantity and does not reserve stock merely because an item is added.

## Orders

There are 12 idempotent order scenarios. They cover pending payment, failed
payment, cancelled, confirmed, shipped, in-transit, out-for-delivery, and
delivered flows. Order creation is always performed through Cart checkout or
the Order API, so product, variant, price, address, subtotal, quantity, and
inventory references are snapshotted by Order Service.

The historical-price scenario stages the T-shirt variant at INR 349 while
`DEMO-MARKETPLACE-ORDER-001` is created, then restores the Catalog price to INR 399. The
existing order keeps INR 349 because Order owns the historical snapshot.

## Payments

All online payments use the repository's `SANDBOX` gateway and signed local
webhooks. The scenarios include pending, failed, captured, and refunded
payments. No external gateway capture is fabricated.

## COD

COD orders are created with `paymentMethod: CASH_ON_DELIVERY`. Payment Service
persists `PENDING_COLLECTION`; it is not marked paid during checkout. One
delivered COD scenario is collected through the protected admin collect API,
and other COD scenarios remain pending collection or shipped.

## Fulfillment

Fulfillments are created through `POST /internal/fulfillments` after the Order
is genuinely eligible. The service creates its own immutable Order snapshot and
starts the supported fulfillment lifecycle at `READY`.

## Shipments

Seven shipments use the deterministic `SANDBOX` carrier and the Shipping
internal shipment API. The runner uses stable `Idempotency-Key` values and
passes exact OrderItem/InventoryUnit references. Current Shipping supports
itemized exact-reservation allocation; partial itemized shipment is therefore
documented as an explicit scenario but is not executed because the current
contract rejects a subset of a reservation during the shipping transition.

## Tracking

Tracking events are sent as signed Sandbox carrier webhooks and cover
`LABEL_CREATED`, `PICKED_UP`, `IN_TRANSIT`, `OUT_FOR_DELIVERY`, and `DELIVERED`
where the service state machine permits them. Tracking numbers and provider
references come from Shipping's Sandbox response; the seed never invents them.

## Demo Scenarios

`data/scenarios.json` contains explicit definitions for browsing, out-of-stock,
low-stock, carts, online success/failure/pending/refund, COD, cancellation,
historical pricing, multiple locations, and the current partial-shipment
limitation.

## Seed Command

Run from the repository root after all backend services are healthy:

```text
python dev-seed/scripts/seed.py
```

The tool also loads a root `.env`. It requires `SEED_ENV=development` or
`SEED_ENV=test`, the eight service URLs, and the development admin credentials
described in `.env.example`.

## Reset Command

```text
python dev-seed/scripts/reset.py
```

Reset requires `SEED_ENV=development` and only runs `down -v` against the eight
named local Compose files in this repository. It is intentionally a full local
development database reset because the services do not expose safe selective
deletion for all orders, payments, shipments, and physical units. It never
accepts a production environment.

## Dry Run

```text
python dev-seed/scripts/seed.py --dry-run
```

Dry run validates the frozen dataset, prints the dependency order and actual
planned counts, and makes no network calls or manifest writes.

## Idempotency

Reruns use stable category slugs, product slugs, variant SKUs, customer emails,
receipt references, reservation references, Order `Idempotency-Key` values,
Payment `Idempotency-Key` values, shipment idempotency keys, and provider event
IDs. Existing catalog records with a different SKU set fail closed and request
the protected development reset instead of silently duplicating or mutating
them.

## Validation

Offline dataset validation:

```text
python dev-seed/scripts/validate.py
```

The live seed run additionally checks service health, catalog counts, physical
inventory totals, active carts, Order SKU references, and the API-returned
relationships. The test suite covers deterministic generation, duplicate and
orphan detection, image metadata/broken assets, dry-run, reset protection, and
explicit unavailable-service errors.

## Image Provenance

The only checked-in images used by this dataset are locally generated PNGs. The
Meesho URL is retained only as source-reference metadata in the JSON documents;
no Meesho image URL is used as a runtime image identity or storage dependency.

## Production Safety

The mutating seed refuses `APP_ENV=production` and refuses any environment
other than `SEED_ENV=development` or `SEED_ENV=test`. Reset is stricter and
requires exactly `SEED_ENV=development`. Do not commit `.env` files, real
secrets, production URLs, or live gateway credentials.

## Troubleshooting

- `401` or `403`: confirm the local Auth admin has the Catalog/Inventory and
  Shipping/Payment permissions used by the APIs.
- Service unavailable: start all eight backend services and their databases;
  the runner stops at the first unavailable dependency.
- Existing SKU mismatch or historical-price mismatch: use the explicit local
  reset command after verifying `SEED_ENV=development`.
- Image upload failure: verify `dev-seed/images/` exists and Catalog's upload
  directory is writable; image rows are never inserted directly into Catalog.
